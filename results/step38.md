# step38 — SMP（对称多核）改为编译期可选特性，默认单核

> 日期：2026-08-30
> 主题：把多核支持从「始终内置」改为「编译选项 `CONFIG_SMP`，默认关闭」，并确立
> **后续开发以单核为主** 的项目路线。
> 结果：单核 / 多核两种构建均编译零警告、QEMU 生产场景启动零 panic，多核能力
> 完整保留在代码树中，`make SMP=1` 一键开启。

---

## 1. 背景与需求

- SukiOS 自 P0-3 起具备完整对称多核能力：INIT-SIPI-SIPI 唤醒 AP、per-CPU
  运行队列 + work-stealing 负载均衡、IPI(0xF0/0xF1/0xF2/0xF3)、TLB shootdown、
  per-CPU GS 数据（`%gs:0` 取 CPU 索引）。
- 但项目当前阶段的开发、验证与调优主线是**单核**：路径简单、可复现，不受跨核
  竞态 / 丢失唤醒等非确定性因素干扰。
- 需求：把 SMP 做成显式编译选项，**默认不开启**；后续开发以单核为主。

设计原则：**单核与多核共用同一套业务代码路径**（调度器/IPC/syscall 快速路径都
以 `cpu_local()->xxx` / `cpu_index()` 编写），切换编译选项时不需要改任何业务
代码，只改变「CPU 槽位数量」与「是否编译 AP 上线路径」。

## 3. 配置注入机制（关键设计）

### 3.1 两级覆盖，任何构建方式语义都确定

1. **构建系统优先**：Makefile 依据 `SMP` 变量生成 `build/config.h`，并以
   `-include $(CONFIG_H)` 插入到**每一个内核编译单元的最前面**（先于任何
   `#include` 生效）。
2. **兜底默认**：`include/kernel/config.h` 内用 `#ifndef CONFIG_SMP` 包裹，
   使不经 Makefile 直接编译（手工 gcc 单文件检查、外部工具扫描）时仍取默认
   单核语义。

```makefile
# Makefile
SMP        ?= 0
CONFIG_SMP := $(if $(filter 1,$(SMP)),1,0)
CONFIG_H   := $(BUILD)/config.h
CFLAGS  += ... -include $(CONFIG_H)
ASFLAGS += ... -include $(CONFIG_H)
```

### 3.2 为什么必须生成头文件，而不是只加 `-DCONFIG_SMP=0`

`-D` 变化**不会**被 make 的时间戳依赖感知，改开关后旧 `.o` 不重编，会产生
「一半单核对象 + 一半多核对象」混链（`percpu_t` 布局 / `MAX_CPUS` 不一致 →
运行期随机崩溃，本项目历史上就出现过同类事故）。

生成 `build/config.h` 后，它由 `-MMD` 自动记录进每个 `.o` 的 `.d` 依赖文件，
**配置内容一变，全部对象自动重编**。Makefile 侧用 `cmp` 比对避免无谓时间戳刷新：

```makefile
$(CONFIG_H): FORCE
	@mkdir -p $(BUILD)
	@printf '/* AUTO-GENERATED by Makefile -- do not edit. */\n'  > $@.tmp
	@printf '#ifndef _SUKI_BUILD_CONFIG_H\n'                     >> $@.tmp
	@printf '#define _SUKI_BUILD_CONFIG_H\n'                     >> $@.tmp
	@printf '#define CONFIG_SMP %s\n' '$(CONFIG_SMP)'            >> $@.tmp
	@printf '#endif /* _SUKI_BUILD_CONFIG_H */\n'                >> $@.tmp
	@if cmp -s $@.tmp $@; then rm -f $@.tmp; else mv -f $@.tmp $@; fi

FORCE:
```

各编译规则追加 order-only 依赖，保证首次构建时配置头先就位：

```makefile
$(BUILD)/%.S.o: %.S | $(CONFIG_H)
$(BUILD)/%.c.o: %.c | $(CONFIG_H)
$(BUILD)/kernel/stack_canary.c.o: kernel/stack_canary.c | $(CONFIG_H)
$(RELK): build/relk.c | $(CONFIG_H)
```

### 3.3 `include/kernel/config.h`（新增）

```c
#ifndef CONFIG_SMP
#define CONFIG_SMP 0          /* 默认：单核 */
#endif

#if CONFIG_SMP
#define CONFIG_SMP_MAX_CPUS 8
#else
#define CONFIG_SMP_MAX_CPUS 1
#endif
```

## 4. 两种构建形态的差异面

### 4.1 `MAX_CPUS`（`include/kernel/percpu.h`）

```c
#include <kernel/config.h>
#define MAX_CPUS CONFIG_SMP_MAX_CPUS   /* 多核 8 / 单核 1（默认） */
```

单核下所有 per-CPU 数组自动收敛为单元素：

- `g_percpu[MAX_CPUS]`（`kernel/arch/x86_64/percpu.c`）
- `g_syscall_kstack[] / g_scratch[] / g_utmp_rsp[]`（`kernel/arch/x86_64/syscall_init.c`）
- `static uint8_t kbuf_cpu[MAX_CPUS][8192]`（`kernel/syscall/syscall.c`）
- `g_gdt_ap[] / g_tss_ap[] / g_ist_ap[] / g_ist2_ap[] / g_gdtr_ap[]`（`kernel/arch/x86_64/gdt.c`）

既省内存，也让「越界访问第二颗 CPU」在编译/链接层面无处可去。

### 4.2 AP 上线路径（`kernel/arch/x86_64/smp.c`）

被 `#if CONFIG_SMP` 包裹、单核构建下**完全不编入镜像**的部分：

- `ap_tramp_start/end`、`ap_mb_cr3/stack/entry/idx` 等跳板符号的 `extern` 声明
- `rdtsc()` / `udelay()`（AP 上线的 INIT-SIPI-SIPI 时序与握手轮询依赖）
- `ap_main()`（AP 的 C 入口：GDT/TSS、IDT、LAPIC、percpu、SMEP/SMAP、syscall MSR、
  LAPIC 100Hz 节拍、idle 循环）
- `smp_init()` 中的跳板拷贝（`0x8000`）、邮箱填写、INIT-SIPI-SIPI、握手轮询、
  IPI 自检

单核分支（`smp_init()` 内）：

```c
#if !CONFIG_SMP
    g_percpu[0].online = 1;
    g_online = 1;
    kprintf("[smp] single-core build (CONFIG_SMP=0): AP startup compiled out, "
            "MADT reports %u LAPIC(s)\n", (unsigned)g_acpi.lapic_count);
    return 1;
#else
    ... 原多核路径 ...
#endif
```

### 4.3 保留的部分（两种构建都有）

**IPI handler 注册不能裁剪**。单核下 `IPI_RESCHED` 以 **self-IPI** 形式承担生存性
职责：`sched.c` 的 `task_publish()`（新建任务发布）与 `sched_wake()`（IPC 唤醒
waiter）都依赖「发一条 RESCHED IPI → handler 内 `schedule()`」来**立即**发生一次
调度。若裁掉它，新建任务只能等 100Hz 节拍兜底，历史上曾表现为「启动挂载卡死」。

保留清单：

- `register_interrupt_handler(IPI_RESCHED / IPI_TLB_FLUSH / IPI_HALT, ...)`
- `isr.S` 中 0xF0/0xF1/0xF2/0xF3 四个向量存根
- `smp_tlb_shootdown()` / `smp_halt_others()`：内部已有 `g_online <= 1` 快速返回，
  单核下自然退化为空操作
- `gdbstub.c` 的 `freeze_others()`：已有 `smp_online_count() > 1` 判断，单核不发冻结 IPI

### 4.4 Makefile 源文件裁剪与 QEMU 联动

```makefile
# 单核构建：剔除 AP 启动跳板（其符号仅被 smp.c 的 #if CONFIG_SMP 分支引用，
# 两者同步裁剪，链接必然自洽）
ifneq ($(CONFIG_SMP),1)
S_SRCS := $(filter-out kernel/arch/x86_64/ap_boot.S,$(S_SRCS))
endif

# QEMU CPU 数随构建配置联动（可用 make run QEMU_SMP=N 显式覆盖）
ifeq ($(CONFIG_SMP),1)
QEMU_SMP    ?= 4
else
QEMU_SMP    ?= 1
endif
```

`make info` 新增输出：

```
SMP       : 0 ( single-core; make SMP=1 to enable)
Config    : build/config.h (CONFIG_SMP=0, MAX_CPUS=1)
QEMU smp  : 1
```

## 5. 使用方法

| 目标 | 命令 | 效果 |
|------|------|------|
| 单核镜像（**默认**） | `make iso` / `make disk` / `make run` | `CONFIG_SMP=0`，`MAX_CPUS=1`，`-smp 1`，无 `ap_boot.S` |
| 多核镜像 | `make iso SMP=1` / `make run SMP=1` | `CONFIG_SMP=1`，`MAX_CPUS=8`，`-smp 4`，AP 全量上线 |
| 单核镜像跑在 4 vCPU 上 | `make run QEMU_SMP=4` | 硬件 4 核但内核不唤醒任何 AP（见 §6 验证 C） |
| 多核镜像只跑 1 vCPU | `make run SMP=1 QEMU_SMP=1` | MADT 仅 1 个 LAPIC，`smp_init` 走「单 CPU 系统」分支 |

切换 `SMP` 开关后**无需手动 clean**：`build/config.h` 经 `.d` 依赖触发全量重编。

## 6. 验证（QEMU，仅 bash + QEMU 自身机制，无任何外部调试器/脚本）

统一手法：`make run-headless QEMU_SERIAL="-serial file:/tmp/x.log" QEMU_AUDIODRV=none`
后台启动 → sleep → `grep` 串口日志判读。

### A. 默认单核构建（clean 后全量重建）

```
$ make clean && make iso
==> Built build/SukiOS.iso
$ cat build/config.h
/* AUTO-GENERATED by Makefile -- do not edit. */
#ifndef _SUKI_BUILD_CONFIG_H
#define _SUKI_BUILD_CONFIG_H
#define CONFIG_SMP 0
#endif /* _SUKI_BUILD_CONFIG_H */
```

- 编译警告数：**0**（顺带修掉了 `spinlock.h` 的 `panic` 隐式声明警告）
- 镜像中 `ap_boot` 出现次数：**0**（跳板已剔除）
- 启动日志关键行：

```
[boot] SMP build config: disabled (single-core) (max_cpus=1)
[percpu] cpu0 installed (lapic_id=0, slot=0x...)
[smp] single-core build (CONFIG_SMP=0): AP startup compiled out, MADT reports 1 LAPIC(s)
[sched] scheduler initialized (SMP RR), idle0 pid=0 stack=0xffffc00080001000
[shell] SukiOS shell online (Ring3, pid via IPC pipeline)
[sched] load balance: 1 CPUs
  cpu0: rq=4 user_switches=294
```

**panic / OOPS 计数 = 0**。

### B. 多核构建（`make iso SMP=1`）

- `gcc` 调用 54 次 → 证明切换开关后**全量重编**生效（无新旧配置混链）
- 启动日志关键行：

**panic / OOPS 计数 = 0**，Ring3 shell 在 4 核上正常调度，多核能力完整保留。

### C. 边界场景：单核镜像 + 4 vCPU 硬件

```
$ make run-headless QEMU_SMP=4 ...
[acpi] MADT: 4 enabled LAPIC(s), IOAPIC @ 0x00000000fec00000 (gsi_base=0)
[boot] SMP build config: disabled (single-core) (max_cpus=1)
[smp] single-core build (CONFIG_SMP=0): AP startup compiled out, MADT reports 4 LAPIC(s)
[sched] load balance: 1 CPUs
  cpu0: rq=4 user_switches=295
```

硬件报告 4 个 LAPIC，但内核**一个 AP 都没唤醒**，全系统只跑 cpu0，零 panic——
证明单核构建的裁剪是彻底的，不存在「意外带起 AP」的隐患。

## 8. 后续路线（已确立）

- **后续开发、验证、调优一律以单核为主**：默认 `make iso` / `make run` 即单核。
- 多核代码保持可编译、可运行（`make SMP=1` 一次验证通过），但不作为日常开发
  与回归基线，避免跨核竞态干扰问题定位。
- 新增子系统时，凡涉及 per-CPU 状态，仍按 `cpu_local()->xxx` / `cpu_index()`
  编写（保持与多核构建兼容），但只需在单核下验证。
